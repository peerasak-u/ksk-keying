บทที่ 3 — สถาปัตยกรรม

เครื่องจักรที่ไม่มีวันลืมงานค้าง

ปัญหาของ headless Claude คือมันจบ process ทันทีที่โมเดลจบเทิร์น — sequencer จึงต้องเป็นโค้ดล้วน ไม่ใช่ AI ที่คุมตัวเอง

แกนกลางของระบบใหม่ทั้งหมดคือ console/sequencer/ — state machine ที่ไม่ใช่ LLM คุมลำดับของ 6 stage ใน ksk-keying เอง (profile → segment → interpret → link → group → categorize → final) โดย spawn แต่ละ stage เป็น claude -p /ksk-stage-<id> คนละ process แยกกัน แทนที่จะสะสมทุก stage ไว้ใน session เดียวที่ยาวขึ้นเรื่อยๆ

มันถูกสร้างขึ้นเป็น prototype วันเดียวกับที่ตัดสินใจทิ้ง Vue console (commit 6782210, 22 กรกฎาคม 2569) — ตอนนั้นยังไม่ผูกกับ console เลย ไม่มี UI ไม่มี resume ตอน crash แต่ทดสอบจริง end-to-end กับลูกค้าตัวอย่าง 216 ครบทุก stage โดยไม่ retry สักครั้ง ให้ผลตรงกับ baseline Ledger Gate เดิม

ทำไมต้องแยก process ต่อ stage

ใน Claude Code แบบ interactive ปกติ orchestrator ส่ง subagent wave ไปทำงานเบื้องหลัง จบเทิร์น แล้วถูกเรียกกลับมาใหม่เมื่อ wave นั้นเสร็จ — claude -p ไม่มีกลไกแบบนั้น process จะปิดตัว ทันทีที่โมเดลจบเทิร์น ซึ่งจะฆ่า subagent wave ที่ยังทำงานค้างอยู่เบื้องหลังไปด้วย

การกำหนดให้แต่ละ stage เป็น process สั้นๆ ที่ตรวจสอบผลลัพธ์ได้จริง (ไม่ใช่การอ่านข้อความที่โมเดลพิมพ์) คือทางแก้ทั้งสองปัญหาพร้อมกัน: process ไม่ยาวจนเสี่ยง context หมดหรือค้างกลางทาง และมี "จุดตรวจสอบ" ที่เป็นโค้ดล้วนๆ คั่นระหว่างทุก stage

สามชนิดของ gate

StageDef.gate เป็น discriminated union สามแบบ:

  • ledger — เรียก ledger.ts --gate จริงสำหรับ segment/interpret/final (Ledger Gate เดิมของ pipeline)
  • shape — stage-shape-check.ts ตัวใหม่ สำหรับ profile/link/group ที่ไม่มี Ledger Gate เป็นของตัวเอง แค่ตรวจว่า artifact ตามสัญญาของ stage นั้นมีอยู่และ parse ได้ — ไม่ใช่การตรวจความถูกต้อง แค่ "process นี้ทำงานเสร็จจริงไหม"
  • categorize — เชื่อมต่อ build-review-data.ts + review-groups.ts เข้าด้วยกัน

ตัดสิน สำเร็จ/ล้มเหลว จาก protocol ไม่ใช่จากข้อความ

spawn-stage.ts อ่านค่า is_error จาก structured result event ของ stream-json protocol บวกกับ exit code — ไม่เคย ใช้วิธี regex ข้อความที่ผู้ช่วยพิมพ์ออกมา และเลือก --permission-mode bypassPermissions แทน acceptEdits เพราะ acceptEdits จะปฏิเสธคำสั่ง Bash ที่ไม่ธรรมดาแบบเงียบๆ ใน headless mode — ซ่อนความล้มเหลว ไว้หลัง is_error: false

รายละเอียดที่ดูเล็กแต่สำคัญ

Directive ของ headless mode ถูกฝังตรงเข้าไปใน prompt ของ -p เอง แทนที่จะใช้ --append-system-prompt — เพื่อให้ยังใช้งานร่วมกับแพ็กเกจ subscription-plan ได้ (ไม่ใช่แค่ API key) รายละเอียดระดับนี้คือสิ่งที่ทำให้ระบบใช้งานได้จริงกับผู้ใช้ทั่วไป ไม่ใช่แค่ demo

เมื่อ sequencer ตัวนี้ถูกโปรโมทเข้า console/app/ ในบทถัดไป มันพา watchdog ติดตัวมาด้วย — กลไกที่คอย "ดัน" งานต่อเมื่อโมเดลจบเทิร์นทั้งที่งานยังไม่เสร็จ ซึ่งจะเล่าละเอียดในบทที่ 4
