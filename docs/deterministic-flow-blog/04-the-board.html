บทที่ 4 — การสร้าง

กระดานงานที่ไม่มีวันหายไปจากตา

Trello-style 3 เลน ที่ไม่เคยว่างเปล่าไปเฉยๆ และ watchdog ที่ดันงานต่อเมื่อ headless Claude หยุดกลางคัน

Issue #38 คือจุดที่ sequencer จากบทที่แล้วถูกโปรโมทเข้า console/app/ จริง พร้อม backend sequencer แบบ in-process (ไม่ spawn child process แยกอีกชั้น) — ตามด้วย #39 ที่ผูกแดชบอร์ดเข้ากับ run state จริงเป็นครั้งแรก

สามเลนที่ไม่มีวันหาย

รูปแบบ UI ที่ล็อกไว้คือกระดาน 3 เลน — รอคิว → กำลังทำงาน → เสร็จสิ้น — ทั้งสามเลน จะแสดงอยู่เสมอตราบใดที่เคยมีงานรันอย่างน้อยหนึ่งครั้ง เลนที่ว่างเปล่าจะโชว์ข้อความ "ว่าง" แทนที่จะ หายไปจากจอ เหมือนคอลัมน์ว่างของ Trello จริง สีของการ์ดเป็นสัญญาณหลักที่มองแวบเดียวรู้สถานะ (สีพื้นอ่อนๆ + เส้นขอบซ้ายเน้นสี ไม่เคยใช้สีจัดเต็ม) และมี รอคิว กำลังทำงาน เสร็จสิ้น ผิดพลาด เป็นตัวหนังสือกำกับ — สีไม่เคยเป็นสัญญาณเดียวที่บอกสถานะ

ปุ่มบนการ์ดเปลี่ยนตามสถานะ: กำลังทำงาน มีปุ่ม "หยุดชั่วคราว" เดียว, รอคิว มีปุ่ม "ยกเลิก" เดียว, เสร็จสิ้น (done) มีสามปุ่ม — "เริ่มใหม่", "ตรวจทาน", และ "เรียนรู้" (ตอนนี้ยังปิดใช้งาน รอบทที่ 7), ส่วน error/stopped มีแค่ "เริ่มใหม่" อย่างเดียว

การตัดสินใจที่ตัดฟีเจอร์ทิ้งไปเลย

ฟีเจอร์ "resume ด้วยข้อความ" ของ console เดิมถูกถอดทิ้งทั้งหมด ไม่ใช่แค่ซ่อน — ไม่มี textarea พิมพ์ข้อความที่ไหนในหน้าจออีก เพราะ session ของ claude -p ที่จบแล้วจะจบจริงๆ ไม่มีทาง continue ด้วยข้อความต่อ ทางเดียวที่จะทำงานลูกค้า/เดือนเดิมต่อคือ "เริ่มใหม่" — POST ไปที่ endpoint เดิม สร้าง run ใหม่ทั้งก้อน ไม่ใช่ resume ของเก่า

คิวเดียวทั่วทั้งระบบ ไม่ใช่ต่อ path

มีงานได้แค่หนึ่งรันพร้อมกันทั่วทั้ง console — ไม่ใช่แค่กันซ้ำต่อ path เดียวกัน การขอรันใหม่ระหว่างที่มีงานอื่นทำอยู่ ไม่ถูกปฏิเสธ แต่ถูกสร้างทันทีในสถานะ queued เรียงตาม queuedAt เมื่องานที่ทำอยู่จบ (ไม่ว่าจะจบแบบไหน — done, error, stopped, หรือกดหยุดเอง) งานที่คิวมานานที่สุดจะเริ่มเองอัตโนมัติ กลไกนี้ทำงานแม้กระทั่งตอน server รีสตาร์ท — เช็คคิวที่ค้างอยู่ตอน boot ทุกครั้ง

Watchdog: ดันงานต่อเมื่อ headless หยุดกลางคัน

ปัญหาจากบทที่แล้ว — claude -p จบ process ทันทีที่โมเดลจบเทิร์น — ถูกรับมือด้วยสองชั้น: directive ที่ฝังไว้ตอน spawn บอกโมเดลตรงๆ ว่า process นี้ headless ห้ามจบเทิร์นจนกว่างานจะเสร็จหรือถึง Ledger Gate จริง และถ้าโมเดลยังจบเทิร์นทั้งที่งานค้างอยู่ (ลืม หรือ wave เสร็จแค่บางส่วน) engine จะอ่านข้อความ result event สุดท้าย: ถ้าเข้าเค้า Ledger Gate จริง (พบคำว่า "ตรวจทาน", "อนุมัติ", "รอ(การ)ตรวจ") ถือว่าจบงานปกติ — แต่ถ้าเข้าเค้างานค้าง (พบคำว่า "กำลัง", "ค้าง", wave, subagent, background) จะ spawn ใหม่ด้วย --resume <sessionId> พร้อมข้อความ watchdog ตายตัว ที่บอกโมเดลชัดๆ ว่าอย่าตีความข้อความอัตโนมัตินี้เป็นการอนุมัติ

กลไกนี้มีเพดานสองชั้น — KSK_AUTO_CONTINUE_MAX (default 8) กันงานเดียวดันตัวเองไม่รู้จบ และ KSK_RUN_BUDGET_USD (default 25) กันค่าใช้จ่ายสะสมทั้งรัน ซึ่งคนละตัวกับ KSK_MAX_BUDGET_USD ที่เป็นเพดานต่อการ spawn หนึ่งครั้งเท่านั้น — รายละเอียดที่ทำให้ การรันจริงกับเงินจริงไม่มีวันหลุดเพดานแบบไม่รู้ตัว
