บทที่ 4 — การสร้าง

แดชบอร์ดที่บอกได้ว่าทุกเดือนอยู่ตรงไหน

หน้าจอเดียวที่อ่านสถานะจากดิสก์จริง ไม่ใช่จากหน่วยความจำของ process — กับคิวที่ปล่อยช่องว่างทันทีที่งานหยุดรอคน

Issue #38 คือจุดที่ sequencer จากบทที่แล้วถูกโปรโมทเข้า console/app/ จริง พร้อม backend sequencer แบบ in-process (ไม่ spawn child process แยกอีกชั้น) — ตามด้วย #39 ที่ผูกแดชบอร์ดเข้ากับ run state จริงเป็นครั้งแรก

ตาราง ไม่ใช่กระดานลากการ์ด

รูปแบบที่ล็อกไว้คือตาราง — ลูกค้าเป็นหัวข้อ เดือนเป็นแถวใต้หัวข้อนั้น สำนักงานบัญชี ไม่ได้ทำงานทีละใบเหมือนการ์ดบนกระดาน แต่ทำเป็นลูกค้า-เดือน และคำถามแรกที่ต้องตอบให้ได้ทุกเช้าคือ "เดือนไหนของใครที่ยังไม่เสร็จ" — ตารางตอบคำถามนั้นได้ในหน้าจอเดียวโดยไม่ต้องเลื่อน แต่ละแถวบอกสถานะ ปริมาณงาน (จำนวนหน้าเอกสาร) เวลาที่คาดว่าจะใช้ และปุ่มสั่งงานของเดือนนั้น

สถานะไม่ได้มีแค่ "เสร็จ/ไม่เสร็จ" แต่มี 11 แบบ เพราะ sequencer แยกแยะได้ละเอียดกว่านั้นจริงๆ — รอคิว กำลังทำงาน กำลังตรวจสอบ (คนละอย่างกัน: อย่างแรกคือ stage กำลังรัน อย่างหลังคือ gate กำลังตรวจผลของ stage นั้นกับหลักฐานบนดิสก์) และที่สำคัญที่สุดคือการแยก ติดขัด (ลองใหม่ได้) ออกจาก หยุดรอมนุษย์ตัดสินใจ — อันแรกกดลองใหม่ได้เลย อันหลังกดไปก็ไม่มีประโยชน์ จนกว่าคนจะเข้าไปตัดสินใจอะไรบางอย่างก่อน สีเป็นสัญญาณช่วย แต่ทุกสถานะมีตัวหนังสือกำกับเสมอ สีไม่เคยเป็นสัญญาณเดียว

การตัดสินใจที่ตัดฟีเจอร์ทิ้งไปเลย

ฟีเจอร์ "resume ด้วยข้อความ" ของ console เดิมถูกถอดทิ้งทั้งหมด ไม่ใช่แค่ซ่อน — ไม่มี <textarea> พิมพ์ข้อความอิสระอยู่ที่ไหนในแอปนี้เลยแม้แต่จุดเดียว เพราะ session ของ claude -p ที่จบแล้วจะจบจริงๆ ไม่มีทาง continue ด้วยข้อความต่อ ทางเดียวที่จะ เดินงานลูกค้า/เดือนเดิมต่อคือปุ่มที่มีความหมายตายตัว — "🔁 ลองขั้นที่ค้างใหม่", "🔄 สร้างข้อมูลรีวิวใหม่" (ประกอบจากที่อ่านไว้แล้ว ไม่เรียก AI ซ้ำ), "♻️ รันซ่อมใหม่ทั้งเดือน" (อ่านเอกสารใหม่ตั้งแต่ต้น เสียเวลาและเงินเต็ม) — แต่ละปุ่มบอกราคาของมันไว้ตรงนั้น ไม่ใช่การพิมพ์บอกโมเดลเอาเองแล้วหวังว่ามันจะเข้าใจ

คิวเดียวทั่วทั้งระบบ ไม่ใช่ต่อ path

โดย default มีงานเดินได้แค่หนึ่งลูกค้า-เดือนพร้อมกันทั่วทั้งแอป (KSK_APP_CONCURRENCY, ปรับขึ้นได้) — ไม่ใช่แค่กันซ้ำต่อ path เดียวกัน การขอรันใหม่ระหว่างที่มีงานอื่นทำอยู่ไม่ถูกปฏิเสธ แต่เข้าคิวรอ แล้วเริ่มเองอัตโนมัติเมื่อมีช่องว่าง

กติกาการถือครองช่องคิวคือจุดที่คิดหนักที่สุด: งานจะถือช่องไว้เฉพาะตอนที่ stage กำลังรันจริง เท่านั้น วินาทีที่มันหยุด — ไม่ว่าจะติดขัด, เจอ env error, หยุดรอมนุษย์, หรือเสร็จ — ช่องถูกปล่อยทันที ผลคือลูกค้าที่ค้างรอคนตรวจอยู่หนึ่งราย ไม่มีวันขวางคิวของลูกค้าที่เหลือทั้งหมด ซึ่งเป็นสิ่งที่จะเกิดขึ้นแน่ๆ ถ้านิยาม "กำลังทำงาน" กว้างกว่านี้

สถานะอยู่บนดิสก์ ไม่ใช่ในหน่วยความจำ

run state ของแต่ละลูกค้า-เดือนถูกเขียนลง ข้อมูลระบบ/_pages/run-state.yaml ในโฟลเดอร์ของเดือนนั้นเอง ไม่ใช่ในฐานข้อมูลกลางของแอป ตอน boot แอปจะเดินอ่าน workspace ทั้งก้อน สร้าง registry ขึ้นใหม่จากไฟล์เหล่านั้น แล้วเอางานที่ยังค้างกลับเข้าคิวเอง

สิ่งที่ได้จากการเลือกแบบนี้คือ container จะถูกลบทิ้งสร้างใหม่กี่รอบก็ไม่มีอะไรหาย และงานของลูกค้า หนึ่งรายย้ายเครื่องได้ด้วยการก๊อปโฟลเดอร์ — เพราะสถานะเดินทางไปพร้อมกับเอกสารเสมอ ไม่ได้แยกกันอยู่คนละที่
