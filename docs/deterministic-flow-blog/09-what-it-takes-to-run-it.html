บทที่ 9 — ภาคผนวก

ติดตั้งใช้งานจริงบน Windows — ทีละขั้น

พัฒนาอยู่บน Linux ก็จริง แต่เครื่องที่ลูกค้าใช้จริงเกือบทั้งหมดคือ Windows — บทนี้เลยเขียนเรียงเป็นขั้นตอนสำหรับ Windows ก่อนเป็นหลัก ทำตามได้โดยไม่ต้องรู้ Docker หรือ Linux มาก่อน ส่วนสรุปสำหรับ Linux/macOS อยู่ท้ายบท

console/ ไม่ใช่แอปที่ต้องการเครื่องแรง — มันเป็น Bun process เดียวที่คอย spawn claude CLI เป็น child process สั้นๆ ต่อ stage งานประมวลผลจริง (การอ่านเอกสาร ตีความ จัดหมวดหมู่) เกิดขึ้นที่ API ของ Anthropic ไม่ใช่บนเครื่องนี้ — เครื่องที่รันแค่ต้องเปิดหน้าเว็บ ให้พนักงานเข้าถึงได้ กับมีสิทธิ์ใช้ claude เท่านั้น

ของที่ต้องมีก่อนเริ่ม

ของที่ต้องมีทำไม
Docker Desktop (Windows 10/11) ตัวที่รันคอนโซลจริง — ไม่ต้องติดตั้ง Bun หรือ Node.js เองเลย ทุกอย่างอยู่ใน container
บัญชี Claude Code ที่ล็อกอินแล้ว บนเครื่อง Windows เครื่องเดียวกัน คอนโซลไม่มีระบบ auth ของตัวเอง — มันยืมไฟล์ credential ที่ Claude Code เวอร์ชัน Windows สร้างไว้ตอนล็อกอินครั้งแรก (subscription หรือ API key ก็ได้)
โฟลเดอร์ลูกค้า ที่จะประมวลผล โฟลเดอร์ที่มีเอกสารดิบของลูกค้าแต่ละราย จัดเป็นโครงสร้าง client/เดือน ตามที่ README ของโปรเจกต์อธิบายไว้
ตัวโปรเจกต์เอง (repo นี้) มี .claude/ (skill + subagent ทั้งหมด) กับ console/ (ตัวเว็บที่กำลังจะติดตั้ง) อยู่ในนั้น

ขั้นตอนติดตั้งบน Windows

ขั้น 1 — ติดตั้ง Docker Desktop

โหลดจากเว็บ Docker แล้วติดตั้งตามปกติ ระหว่างติดตั้งจะมีตัวเลือกให้เปิดใช้ WSL2 backend — เลือกใช่ (เป็นค่า default อยู่แล้วในเวอร์ชันปัจจุบัน ไม่ต้องเปลี่ยนอะไร) เปิดเครื่อง ใหม่ถ้าติดตั้งขอ แล้วเปิด Docker Desktop ขึ้นมาค้างไว้ (ต้องเปิดอยู่ตลอดเวลาที่จะรันคอนโซล)

ขั้น 2 — ติดตั้งและล็อกอิน Claude Code บน Windows

ติดตั้ง Claude Code เวอร์ชัน native สำหรับ Windows ตามเอกสารของ Anthropic แล้วรันคำสั่ง claude ครั้งหนึ่งเพื่อล็อกอิน (subscription plan หรือ API key ก็ได้) — ขั้นตอนนี้จะสร้าง ไฟล์ .claude\.credentials.json และ .claude.json ไว้ในโฟลเดอร์โปรไฟล์ผู้ใช้ ของ Windows (C:\Users\ชื่อผู้ใช้\) โดยอัตโนมัติ — คอนโซลจะยืมไฟล์สองตัวนี้ไปใช้ในขั้นถัดไป ไม่ต้องเปิดเองหรือย้ายไปไหน

ขั้น 3 — วางโปรเจกต์และโฟลเดอร์ลูกค้าไว้ในเครื่อง

คัดลอกโฟลเดอร์โปรเจกต์นี้ไปไว้ที่ไหนก็ได้บนเครื่อง Windows เช่น C:\ksk-keying\ — แล้วเตรียมโฟลเดอร์ที่เก็บข้อมูลลูกค้าจริงไว้อีกที่หนึ่ง (จะอยู่ในนี้หรือแยกไดรฟ์ก็ได้ ขอแค่รู้ path เต็ม)

ขั้น 4 — เปิด PowerShell แล้วเข้าโฟลเดอร์ console

cd C:\ksk-keying\console

ไม่ต้องเปิด WSL shell เองแยกต่างหาก — พิมพ์คำสั่ง docker/docker compose จาก PowerShell ตรงๆ ได้เลย (ดูกล่อง "ทำไมพิมพ์จาก PowerShell ได้" ท้ายบทถ้าอยากรู้ว่าทำไม)

ขั้น 5 — สร้างไฟล์ .env

คัดลอก .env.example เป็น .env ในโฟลเดอร์เดียวกัน แล้วแก้ค่าให้ตรงกับ เครื่องจริง — ใช้ forward slash (/) ในทุก path แม้จะอยู่บน Windows (เป็น syntax ที่ Docker Desktop คาดหวัง ไม่ใช่ backslash แบบ path ปกติของ Windows): 

UID=1000
GID=1000
HOST_HOME=C:/Users/ชื่อผู้ใช้

KSK_APP_PORT=8940
KSK_APP_HOST=0.0.0.0
KSK_APP_WORKSPACE_ROOT_HOST=C:/ksk-keying/samples/clients
KSK_APP_SKILLS_HOST=C:/ksk-keying/.claude
ตัวแปรคือ path ไปที่ไหน
HOST_HOME โฟลเดอร์โปรไฟล์ผู้ใช้ Windows — ที่เก็บไฟล์ credential จากขั้น 2
KSK_APP_WORKSPACE_ROOT_HOST โฟลเดอร์ที่เก็บลูกค้าทั้งหมด (แต่ละโฟลเดอร์ย่อยคือลูกค้าหนึ่งราย) — จากขั้น 3
KSK_APP_SKILLS_HOST โฟลเดอร์ .claude\ ของตัวโปรเจกต์เอง — ถ้า path นี้ผิดหรือไม่ได้ mount เข้าไป /ksk-keying จะกลายเป็น no-op เงียบๆ ที่รายงานว่า "เสร็จ" ทั้งที่ไม่ได้ ทำงานอะไรเลย เป็นจุดพลาดที่พบบ่อยที่สุด

ขั้น 6 — สร้าง image แล้วสั่งรัน

docker compose build ksk-app
docker compose up -d ksk-app

รอบแรกจะใช้เวลาสักครู่ (ดาวน์โหลด base image + ติดตั้ง Claude Code CLI ข้างในให้อัตโนมัติ) รอบถัดๆ ไป จะเร็วขึ้นมากเพราะ Docker cache ชั้นที่ไม่เปลี่ยนไว้ให้แล้ว เช็คว่า container ขึ้นจริงด้วย: 

docker compose ps

ควรเห็นสถานะ Up สำหรับ service ksk-app

ขั้น 7 — เปิดใช้งาน

เปิดเบราว์เซอร์ไปที่ http://localhost:8940 (หรือพอร์ตที่ตั้งไว้ใน KSK_APP_PORT) ควรเห็นหน้า dashboard พร้อมรายชื่อลูกค้าทั้งหมดที่อยู่ในโฟลเดอร์ที่ชี้ไว้ตอนขั้น 5 — ถ้าเห็นรายชื่อ ครบ แปลว่าทุก mount ถูกต้องแล้ว พร้อมใช้งานจริง

ครั้งต่อไปไม่ต้องทำซ้ำทุกขั้น

ขั้น 1–5 ทำครั้งเดียว หลังจากนั้นแค่เปิด Docker Desktop แล้วรัน docker compose up -d ksk-app จากโฟลเดอร์ console\ ก็พอ จะปิดใช้งานก็ docker compose stop ksk-app — ข้อมูลลูกค้าและสถานะการรันทั้งหมดอยู่ในโฟลเดอร์ workspace ที่ mount ไว้ ไม่ได้ อยู่ใน container จะลบ/สร้าง container ใหม่กี่ครั้งก็ไม่เสียงาน

ปัญหาที่เจอได้บ่อย

อาการสาเหตุที่เป็นไปได้มากที่สุด
เปิด localhost:8940 ไม่ขึ้นเลย Docker Desktop ยังไม่เปิด หรือ container ยังไม่ขึ้น — เช็คด้วย docker compose ps แล้วดู log ด้วย docker compose logs ksk-app
dashboard ขึ้นแต่ไม่มีรายชื่อลูกค้าเลย หรือมีไม่ครบ KSK_APP_WORKSPACE_ROOT_HOST ใน .env ชี้ผิดโฟลเดอร์ — เช็ค path อีกครั้ง แล้ว docker compose up -d ksk-app ใหม่ (ต้อง recreate container ถึงจะอ่านค่า .env ใหม่)
รันงานจริงแล้ว "เสร็จ" ทันทีโดยไม่ทำอะไรเลย ไม่มี error KSK_APP_SKILLS_HOST ชี้ผิด หรือไม่ได้ mount — /ksk-keying กลาย เป็นคำสั่งที่ไม่รู้จักแบบเงียบๆ อาการนี้หลอกง่ายที่สุดเพราะดูเหมือนสำเร็จ
ล็อกอิน Claude Code ใหม่ทุกครั้งที่รัน / ถามให้ล็อกอินซ้ำ HOST_HOME ผิด หรือยังไม่ได้ล็อกอิน Claude Code บน Windows host เลยตั้งแต่ขั้น 2 — ไฟล์ credential ต้องมีอยู่จริงที่ path นั้นก่อน mount ถึงจะมีอะไรให้ยืม

ประสิทธิภาพบน Windows: เบาพอ มีจุดเดียวที่ควรรู้

CPU/RAM ของงานจริง (spawn claude CLI สั้นๆ ต่อ stage, เสิร์ฟหน้าเว็บเบาๆ) ไม่ใช่ปัญหา — WSL2 ที่ Docker Desktop ใช้เป็น engine เบื้องหลังนั้นเบามาก overhead ต่ำกว่ายุค Hyper-V เก่ามาก จุดเดียวที่ควรรู้ไว้คือ I/O ข้ามขอบเขตไฟล์ระบบ Windows↔Linux — ถ้าโฟลเดอร์ลูกค้าที่ mount เข้าไปอยู่บน C:\... ตรงๆ (ตามขั้นตอนด้านบน) การอ่าน/เขียนไฟล์จำนวนมาก (PDF หลาย ร้อยหน้า, JSON ย่อยต่อกลุ่มเอกสาร) จะช้ากว่าไฟล์ที่อยู่ในระบบไฟล์ของ WSL2 เองล้วนๆ อย่างเห็นได้ชัด — งานของคอนโซลนี้เบาพอที่จะไม่เจ็บตัวมากในการใช้งานทั่วไป แต่ถ้าลูกค้ารายไหนมีเอกสารสแกนเยอะมากต่อเดือน การย้าย workspace ของลูกค้ารายนั้นมาเก็บในระบบไฟล์ของ WSL2 เอง (ผ่าน \\wsl$\...) จะเร็ว กว่า bind-mount ข้ามจาก Windows ตรงๆ อย่างมีนัยสำคัญ — ไม่จำเป็นสำหรับการใช้งานทั่วไป เก็บไว้เป็นทาง เลือกถ้าเจอปัญหาความเร็วจริงๆ

ทำไมพิมพ์จาก PowerShell ได้เลย ไม่ต้องเปิด WSL shell เอง

Docker Desktop บน Windows ใช้ WSL2 เป็น engine เบื้องหลังอยู่แล้วโดย default — ไม่ว่าจะสั่งงานจาก PowerShell, CMD, หรือ WSL shell เอง คำสั่ง docker ทุกตัวก็วิ่งผ่าน WSL2 VM เดียวกันอยู่ดี ต่างกันแค่ "หน้าต่างที่พิมพ์คำสั่ง" ไม่ใช่ "ตัวที่รันงานจริง" — Docker Desktop จัดการ WSL2 ให้ทั้งหมดอยู่แล้ว ไม่ต้องตั้งค่าอะไรเพิ่ม

สรุปสำหรับ Linux / macOS

ขั้นตอนเดียวกันทั้งหมด (docker compose build ksk-app แล้ว docker compose up -d ksk-app) ใช้ path แบบ Unix ปกติใน .env ได้เลย (เช่น HOST_HOME=/home/ชื่อผู้ใช้) — บน Linux ตัว compose ใช้ network_mode: host ทำให้ localhost:8940 เข้าถึงได้ตรงๆ โดยไม่ต้อง map พอร์ตเอง เหมือนที่ deployment จริงของโปรเจกต์นี้เองรันอยู่บน Raspberry Pi ก็ใช้เส้นทางนี้ ถ้าจะรันตรง บนเครื่องโดยไม่ผ่าน Docker เลยก็ทำได้เช่นกัน — ตัวเดียวที่ต้องมีคือ Bun (ไม่ต้องมี Node.js) แล้วสั่ง bun run app/server.ts จากโฟลเดอร์ console/ โดยตั้งตัวแปรแวดล้อมชุดเดียวกัน กับใน .env ตรงๆ แทนการอ่านจากไฟล์
