บทที่ 7 — สิ่งสุดท้ายบนแผนที่

ปิดวงจรการเรียนรู้

จากการแก้ไขของมนุษย์หนึ่งจุด ไปสู่ coa_usage.json ที่ฉลาดขึ้น และบันทึกที่ ksk-magnum อ่านจริงตอนรับลูกค้าใหม่

Issue #43 คือ ticket สุดท้ายบนแผนที่ #29 — เมื่อปิด แผนที่ทั้งใบก็ถึงจุดหมายที่เขียนไว้ตั้งแต่บทที่ 2 โจทย์คือกลไกไฮบริดที่ ticket #37 ตัดสินใจไว้ก่อนแล้ว: สคริปต์แบบ deterministic เดินดู changes.json ของทุกกลุ่มทุกเดือนของลูกค้าคนหนึ่ง (ไม่ใช่แค่เดือนที่กด ปุ่ม) นับเฉพาะการแก้ไข field: "account_code" ที่บทที่แล้วเพิ่งแก้ชื่อให้ตรงกัน แล้วเสนอชุดอัปเดต coa_usage.json — จากนั้น agent pass เบาๆ ตรวจสอบก่อนที่จะยืนยันจริง

ครึ่งที่เป็นโค้ดล้วน กับครึ่งที่เป็นวิจารณญาณ

learn.ts ฝั่ง deterministic แบ่งเป็นสองโหมด: --propose เดินดูทุกเดือน นับเฉพาะการแก้ไขบัญชี พิมพ์ชุดข้อเสนอ (ksk_learn_report.v1) ออกมาโดยไม่เขียนอะไรเลย ส่วน --apply รับสิ่งที่มนุษย์ยืนยันแล้วมา upsert แบบบวกเพิ่มเท่านั้น (ไม่เคยทับ) — hint เดิมที่มีคนเขียน label/notes ไว้ด้วยมือจะไม่หายไป

รายละเอียดที่ทำให้ระบบนับซ้ำไม่ได้

ความ idempotent ของระบบนี้อยู่ที่ระดับ "การแก้ไขแต่ละครั้ง" ไม่ใช่ระดับไฟล์ — เพราะ changes.json คือ snapshot ที่คำนวณใหม่ทุกครั้งที่ export (มี computed_at สดใหม่เสมอ) ถ้าใช้ watermark ระดับไฟล์ การ export เดือนเดิมซ้ำโดยไม่มีอะไรเปลี่ยนจะนับการแก้ไขเดิมซ้ำ ทุกครั้งที่ export ใหม่ — ทดสอบจริงแล้ว: แก้ไข → export → learn → export ซ้ำ → learn ซ้ำ ตัวนับยังคงเป็น 1

ฝั่ง agent (sonnet หนึ่งรอบ ผูกกับปุ่ม "🎓 เรียนรู้จากการแก้ไข" ในเมนู ⋯ ต่อเดือนบนแดชบอร์ด) ทำหน้าที่ ตัดสินว่าข้อเสนอไหนเป็น "แพทเทิร์นจริง" กับไหนเป็น "ข้อยกเว้นครั้งเดียว" — เป็นแค่คำแนะนำ อ่านอย่างเดียว ไม่มีสิทธิ์เขียนอะไรจนกว่ามนุษย์จะกดยืนยัน และถ้า pass นี้ล้มเหลว timeout หรือ parse ไม่ได้ ข้อเสนอทุกอันจะอยู่ในสถานะ "ยังไม่ตรวจ" ให้มนุษย์ตัดสินใจเองล้วนๆ

สัญญาณที่ใหญ่กว่าการอัปเดตหนึ่งบรรทัด

ticket #37 เปิดพื้นที่ไว้ตั้งใจว่า "บางครั้งแพทเทิร์นการแก้ไขอาจสมควรได้มากกว่าการ bump coa_usage.json" — โดยไม่บอกรูปร่างชัดเจนล่วงหน้า ผลที่ #43 ตัดสินใจคือเขียนบันทึกลง learning-notes.md ที่ root ของลูกค้า — แต่พอสร้างเสร็จก็พบว่าไฟล์นี้ "เขียนได้อย่างเดียว" ไม่มี agent ไหนอ่านมันเลย ข้อสังเกตที่ AI เห็นและมนุษย์ยอมรับ ไม่มีผลอะไรกับการรันครั้งถัดไปสักนิด

#47 — ปิดวงจรจริง

Ticket #47 แก้ช่องโหว่นี้เป็นสองด้าน: มนุษย์อ่านและ "เคลียร์" บันทึกได้ในไดอะล็อกเรียนรู้เดิม ผ่าน checkbox markdown ธรรมดา (- [ ] **หัวข้อ** — รายละเอียด → - [x]) — เลือกวิธีนี้แทน การทำ archive section หรือไฟล์ .done.md แยก เพราะไฟล์เดิมเป็นแบบ append-only การติ๊กบรรทัดเดียวจึงไม่มีวันชนกับบล็อกวันที่ใหม่ที่ learn --apply เขียนต่อท้ายเสมอ

และด้านที่สอง: ksk-magnum — agent รับลูกค้าใหม่ตอน Stage 0 — อ่านบันทึกที่ยังไม่ถูกจัดการ ตอนร่าง CLIENT.md จริง โดยชั่งน้ำหนักมันเหมือนกับ convention ที่ติด flag assumption ไว้แล้ว ไม่เคยถือเป็นใบอนุญาตให้ mapping ความมั่นใจสูง — เพราะบันทึกพวกนี้คือ "ข้อเสนอที่ AI เขียน มนุษย์เก็บไว้" ไม่ใช่กฎที่ยืนยันแล้ว

รายละเอียดเล็กที่กันบั๊กจริง: handled เป็นฟิลด์ที่ไวต่อ "การมีอยู่" — อาเรย์ว่างเปล่า [] หมายถึง "ยกเลิกการจัดการทุกบันทึก" (มนุษย์ติ๊กกล่องสุดท้ายออกเพื่อเปิดใหม่) ส่วนฟิลด์ที่ไม่มีเลยหมายถึง "ไม่แตะการจัดการ" — ถ้าปฏิบัติกับ [] เหมือน "ไม่มีอะไรต้องทำ" คำสั่งเดียวที่มากับ request แบบยืนยันเฉพาะบันทึกจะถูกทิ้งแบบเงียบๆ

เมื่อ #47 ปิด แผนที่ #29 ทั้งใบก็ถึงปลายทางที่เขียนไว้ตั้งแต่บทแรก — ระบบ keying เอกสารทั้งชุด เดินจากโฟลเดอร์ดิบไปจนถึง PEAK export ผ่านเว็บแอปตัวเดียว และวงจรการแก้ไขของมนุษย์ก็ย้อนกลับไป สอนทั้ง coa_usage.json และการรับลูกค้าครั้งถัดไปได้จริง ไม่ใช่แค่บันทึกทิ้งไว้เฉยๆ
