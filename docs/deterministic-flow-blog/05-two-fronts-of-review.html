บทที่ 5 — การรีวิว

สองสนามรบของการตรวจทาน

ก่อนถึงหมวดหมู่บัญชี ต้องผ่านด่านตัดออก/ซ้ำก่อน — และบั๊กจริงหนึ่งตัวที่ code review สองแกนจับได้ก่อนขึ้นจริง

แผนที่ #29 ล็อกลำดับความสำคัญไว้ตั้งแต่บทที่ 2: รีวิว "ตัดออก/ข้าม" มาก่อน รีวิวหมวดหมู่บัญชีมาทีหลัง — สองสนามนี้กลายเป็นสองกลุ่ม ticket คนละชุดที่ landed ห่างกันแค่ไม่กี่วัน

สนามที่หนึ่ง: ตัดออก ซ้ำ และการแก้คืน

Issue #33 วางกลไกไว้ก่อนสร้าง: การยืนยันข้อเสนอตัดออกของ AI เขียนเป็น entry ใน dispositions.yaml พร้อม declared_by: human — ผนึกด้วยกลไก PROTECTED_DECLARERS ที่มีอยู่แล้ว กลายเป็น audit trail จริง ส่วนการ "แก้คืน" (overturn) ข้อเสนอตัดออก จะรีเซ็ต sequencer กลับไปที่ stage segment แล้วเดินหน้าใหม่ทั้งลูกค้า/เดือนนั้นจนถึง final — เหมือนกับ retry ปกติทุกประการ ไม่ใช่การ resume แบบละเอียด (ถูกปฏิเสธไว้ตั้งแต่ตอนออกแบบว่าไม่จำเป็น)

สาม build ticket ถัดมา — #44 (core loop), #45 (XLSX + duplicate-pane preview), #46 (bring-back + repairRun) — สร้างหน้ารีวิวตัดออกให้ตรงกับ prototype ของบทที่ 2 เป๊ะ: จอแบ่งครึ่งเต็มความสูง viewer ซ้าย ลิสต์คำกล่าวอ้างขวา

สนามที่สอง: หมวดหมู่บัญชีและ export

Issue #41 สร้างหน้ารีวิวหมวดหมู่/กลุ่มเอกสาร ตามด้วย #42 ที่ปิดวงจรด้วย human-edit changelog + server-side PEAK export จริง — สามไฟล์ใหม่ที่เป็นแกนของบทนี้:

  • group-source.ts — ประกอบสร้างข้อมูล "ต้นฉบับที่ AI สร้าง ไม่เคยถูกมนุษย์แก้" ของกลุ่มหนึ่งขึ้นมาใหม่จาก interpretation.json+categorize.json ตรงๆ (พอร์ตมาจาก logic ของ pipeline เดิม แต่ตัดให้เหลือแค่ที่ changelog ต้องใช้)
  • changelog.ts — เทียบ review-data.json ปัจจุบันกับข้อมูลต้นฉบับที่ประกอบขึ้นใหม่ กลายเป็น changes.json ต่อกลุ่ม (สคีมา ksk_review_changes.v1)
  • peak-export.ts — ตัวสร้างแถว PEAK XLSX จริง พอร์ตมาจากสคริปต์เดิม ประกอบเป็น workbook จริงผ่านแพ็กเกจ xlsx

การตัดสินใจที่ตั้งใจให้ "แคบ": แทนที่จะพอร์ตโมเดล committed/skipped/reviewed/note แบบเต็มของ Vue app เดิม #42 เพิ่มแค่ บูลีนเดียว — skipped — ต่อหน้า/แถว เป็นประตูออก เหตุผลคือ พอถึงขั้นรีวิวหมวดหมู่ เอกสารผ่านการรีวิวตัดออกมาแล้วรอบหนึ่ง ขั้นนี้แค่ต้องการทางออกฉุกเฉินให้ผู้ตรวจที่เจอ อะไรหลุดมา ไม่ใช่การกดยืนยันทีละเอกสารซ้ำอีกรอบ (ซึ่งจะเป็นแรงเสียดทานจริงคูณด้วยหลายร้อยเอกสารต่อเดือน)

บั๊กจริงที่ code review สองแกนจับได้

changelog.ts เดิมส่งออก entry การเปลี่ยนหมวดบัญชีเป็น field: "account_key" — ตรงกับศัพท์ของกลไก edit-PATCH ใน review-edit.ts เอง แต่ ticket #36 ที่ปิดไปแล้ว ระบุไว้ชัดว่า pass การเรียนรู้ในอนาคต (ticket #37) จะกรอง changelog entry ด้วยคำเป๊ะๆ ว่า field: "account_code" ถ้าไม่แก้ ตัว #37 ที่จะสร้างต่อจะจับ entry ของ #42 ได้ ศูนย์รายการ แบบเงียบๆ — ไม่ใช่แค่การตั้งชื่อผิด แต่เป็นช่องโหว่ทำลาย contract ที่มีเอกสารรองรับระหว่างสอง ticket ถูกแก้ก่อน commit โดยเปลี่ยนชื่อ field ที่ส่งออกเป็น "account_code" (ค่าที่เก็บจริงไม่เปลี่ยน)

ทดสอบกับข้อมูลจริง ไม่ใช่ mock

smoke test จริงกับลูกค้า 216/เดือนพฤษภาคม (สำเนา scratch ไม่แตะ samples/ ต้นฉบับ ตามกฎ CLAUDE.md) แก้ไขจริงหนึ่งจุด ข้ามหนึ่งกลุ่ม — changes.json ของทั้งสองกลุ่มถูกต้องเป๊ะ (คนละหนึ่งรายการ) ส่วนอีกสองกลุ่มที่ไม่แตะเลยกลับมาเป็น entries: [] ว่างเปล่า — ไม่มี false positive สักตัวข้ามข้อมูล production จริง ส่วน export รายการเดินบัญชีธนาคาร 328 แถว (ข้าม 1) สมดุลเป๊ะ: 327 รายการที่ commit → 654 ขาเดบิต/เครดิต รวม ฿3,393,688.51 ทั้งสองฝั่งเท่ากัน
