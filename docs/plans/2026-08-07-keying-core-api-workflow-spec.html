Keying Core — /v1 API · เครื่องสถานะ workflow · CLI

ระดับถัดจาก แผนสถาปัตยกรรม revision 4 — แผนบอกว่ามีเส้นทางอะไรบ้าง (§9.1 = 21 เส้นทาง), มี event ชื่ออะไรบ้าง (§10.3), และ CLI มีคำสั่งอะไรบ้าง (§11). เอกสารนี้ลงรายละเอียดจน เขียนโค้ดได้โดยไม่ต้องคิดสัญญาเพิ่มเอง — พารามิเตอร์ สคีมา รหัสสถานะ ทุกทรานซิชัน ทุก exit code. §21 ปิดแล้ว ไม่มีอะไรถูกเปิดใหม่.

แผนสถาปัตยกรรมเป็นเจ้าของ — ไม่แตะ

ขอบเขตระหว่างสองบริการ · ใครเป็นเจ้าของ entity ไหน · §21 ทั้งหกข้อ (ไม่มีประวัติการรัน · personId ถาวร · monthId = YY-MM · SQLite หนึ่งไฟล์ต่อบริการ · login ของแพลตฟอร์มเอง · งวดที่ไม่มีเดือนไม่ถึง Core)

สี่ข้อที่ควรใช้เวลาตรวจสักนาที

ทั้งเอกสารมี 35 จุดที่ผู้เขียน “เลือกเอง” เพราะสถาปัตยกรรมไม่ได้ชี้ขาด — ทุกจุดมีเครื่องหมาย C-nn และรวมไว้ที่แท็บสุดท้าย. สี่ข้อนี้คือข้อที่กัปตันน่าจะอยากตัดสินเอง.

สิ่งที่ต้องรู้ก่อนอ่านที่เหลือ

สองแกน ไม่ใช่แกนเดียว. สภาพของ run คือ คู่ — สถานะ sequencer (10 ค่า) กับ ตำแหน่งใน scheduler (queued / active). แผน §9.3 สั่งให้แยกกันไว้ เอกสารนี้บังคับตาม: status คือค่าดิบ, observedStatus เป็นค่าที่คำนวณเพิ่ม ไม่เคยแทนที่ค่าดิบ.
repair ลบงานที่คนตรวจไว้. การซ่อมรีเซ็ต run กลับไป Stage 1 แล้วเขียนทับ _segments/**, _doc_groups/**, ตรวจทาน/** ทับที่เดิม — ทุกการแก้ไขที่คนทำผ่าน PATCH …/groups/… หายหมดและกู้ไม่ได้. นี่คือราคาของ §21 “ไม่มีประวัติการรัน” ที่โผล่ขึ้นมาที่ API และ เอากลับเข้ากระบวนการ (keep) ก็เรียก repair เหมือนกัน. หน้าจอที่มีปุ่มนี้ต้องบอกผู้ใช้ในคลิกเดียวกัน.
Core เซ็นชื่อใน Gate ไม่ได้ — โดยโครงสร้าง. ไม่มีเส้นทาง ไม่มี event ไม่มีฟิลด์. “ห้าม auto-pass” จึงไม่ใช่กติกาที่ใครต้องจำ (แผน §2.3, §20).

สิ่งที่เอกสารนี้จงใจไม่ตัดสิน

  • หน้าจอของแพลตฟอร์มสำหรับ run ที่หยุดรอคน (§23.3 ครึ่ง “การแสดงผล”) — ครึ่ง “สัญญา” เติมครบแล้ว
  • ใครเป็นเจ้าของข้อมูลลูกค้าตัวจริง (§23.4) — /coa เปิดเพราะ §9.1 สั่ง เท่านั้น
  • event log ของการเปลี่ยนเฟส (§23.5) — เป็นเรื่องของแพลตฟอร์ม phase 7
  • ควรเพิ่ม KSK_APP_CONCURRENCY ไหม (§23.8) — วัดก่อน
  • RunGroup.kept (§23.8) — ไม่มีที่ลงในไฟล์จริง จึงไม่อยู่ในสัญญา

เครื่องสถานะ workflow

นี่คือเครื่องใน console/sequencer/logic.ts บวกมิติ scheduler ใน console/app/orchestrator.ts — ไม่ได้ประดิษฐ์ใหม่. คลิกที่กล่องเพื่อกรองตารางทรานซิชันด้านล่าง.

ปกติ / ระหว่างทาง พักได้ ลองใหม่ได้ (retry) ปลายทาง ต้องมีคนจัดการ สำเร็จ รางกลับ (retry / repair)

แถวนี้คือค่าที่ client ได้กลับไปใน details.allowedCommands และในทุกการอ่าน GET /v1/jobs/{jobId} — client ไม่ต้องคำนวณเอง.

สามสถานะที่หยุดรอคน — เติมช่องว่าง §23.3

แผน §23.3 บอกว่า mock ไม่มีแนวคิดของ run ที่หยุดรอคน และให้ผู้ลงมือเติมเอง นี่คือการเติม — จำกัดอยู่แค่สิ่งที่ §7 กับ §9.1 มีอยู่แล้ว ไม่มีเส้นทางใหม่ ไม่มีความสามารถใหม่.

สถานะเกิดอะไรขึ้นอะไรเคลียร์ได้ใครต้องทำ
C-13 Core ไม่มีเส้นทางสำหรับ “ปลดล็อก” human stop. ทางออกคือคนไปจัดการ human-stop.yaml นอกระบบ แล้วสั่ง repair — sequencer ไม่เคยล้างไฟล์นั้นเอง (logic.ts:64) และ §9.1 ก็ไม่มีเส้นทางให้ล้าง.

เส้นทาง /v1 — ครบทั้ง 21 แถวของ §9.1

เรียงตามลำดับในตาราง §9.1 ไม่มีแถวไหนหายไป. คลิกเพื่อกางสคีมา. ทุกเส้นทางยืนยันตัวตนด้วย service token และอาจตอบ 401 503 500 ได้เสมอ — ไม่เขียนซ้ำในแต่ละเส้นทาง.

      C-14 ลำดับคิวหลังรีสตาร์ตคือลำดับการเดินโฟลเดอร์ ไม่ใช่ลำดับที่เคยเข้าคิว.
      ลำดับเดิมไม่ได้ถูกบันทึกไว้ที่ไหน และการบันทึกมันคือการเพิ่มตารางลำดับถาวร ซึ่ง §8.2 ห้าม.
      ลำดับใหม่ยัง deterministic (เรียงแบบไทย) — แค่ไม่ใช่ลำดับเดิม. ไม่กระทบความถูกต้อง.
