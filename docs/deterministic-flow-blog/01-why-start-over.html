บทที่ 1 — จุดเริ่ม

ทำไมต้องทิ้งของเดิมแล้วเริ่มใหม่

Vue console + SQLite เพิ่งสร้างเสร็จและ commit ไปเมื่อวันก่อน แต่เจ้าของโปรเจกต์เปิดแผนที่ใหม่ทั้งแผ่นแทนที่จะแก้ของเดิม

ก่อนจะมาเป็น console/ อย่างที่เห็นทุกวันนี้ มันเคยเป็น Vue app ที่พ่วง SQLite มาก่อน — งานนี้ชื่อ "review console migration" เริ่มไปได้ไกลจนถึงขั้นมี ADR ของตัวเอง (docs/adr/0001), มีสคีมาที่ตั้งชื่อเวอร์ชันแล้ว (ksk_review_human_state.v1, ksk_review_changelog.v1), มี events taxonomy, มี wayfinder map เดินไปแล้ว 16 ticket (issue #1) จนถึงจุดที่ commit 5332e01 ปิดงาน Phase 2 ทั้งชุด — dashboard, drafts, learn, event history, ครบ.

แล้ววันที่ 24 กรกฎาคม 2569 เจ้าของโปรเจกต์ก็ตัดสินใจว่า "แนวทางนี้ทำงานได้ไม่ดีพอ" — ไม่ใช่บั๊ก ไม่ใช่ scope ที่ขาด แต่เป็นการตัดสินใจระดับสถาปัตยกรรม จึงเปิดแผนที่ wayfinder ใบใหม่ (issue #29) แล้วปิด issue #1 ทิ้ง พร้อมคอมเมนต์ชี้กลับมาที่แผนที่ใหม่ — สคีมา, ADR 0002, events taxonomy, Vue+SQLite console ทั้งหมดที่ #1 ตัดสินใจไว้ **ไม่ถูกนำมาใช้ซ้ำ** อย่างเป็นทางการ

บันทึกการตัดสินใจ

"Owner's call: that approach didn't work out well enough — start fresh here." ประโยคเดียวในตัว issue #29 เอง คือคำอธิบายทั้งหมดที่มีบันทึกไว้ว่าทำไมถึงทิ้งงานที่เสร็จแล้วทั้งชุด แผนที่ใหม่ยังคงบอกไว้ชัดว่า #1 "carries execution as well as decisions" — เหมือนกับที่ #29 เองก็จะทำ นั่นคือรูปแบบการทำงานที่ตกลงกันไว้: แผนที่บางใบไม่ใช่แค่ตัดสินใจแล้วส่งต่อให้คนอื่นสร้าง แต่ตั๋วสร้างจริงก็อยู่บนกระดานเดียวกัน ปลดล็อกเมื่อตั๋วตัดสินใจของมันปิด

สิ่งที่รอดมาจากของเก่า

ไม่ใช่ทุกอย่างถูกทิ้ง — พื้นฐานที่แผนที่ #29 ยึดเป็น ground truth ใหม่คือของที่ "ทำงานได้จริง" อยู่แล้ว:

  • Sequencer แบบ deterministic (console/sequencer/{logic.ts,spawn-stage.ts,completion-check.ts}) — เพิ่งถูกสร้างเป็น prototype วันเดียวกับที่ตัดสินใจทิ้งของเก่า (ดูบทที่ 3) แล้วถูกโปรโมทขึ้นเป็นแกนกลางของระบบใหม่ทันที
  • โครง app skeleton — run-store.ts, orchestrator.ts, workspace.ts, config.ts, server.ts ในโฟลเดอร์ console/app/ คือโค้ดที่ตัวแผนที่ #29 เองระบุไว้เป็น ground truth
  • กฎเดิมของ repo ที่ไม่เปลี่ยน: CLAUDE.md — กฎห้ามแตะ answer-keys, model tier ของ agent team, ขอบเขตการ sync ไป Dropbox

กติกาที่วางไว้ก่อนเริ่ม

สิ่งที่ต่างจากรอบก่อนคือแผนที่ #29 มา "พร้อมกติกามาตรฐาน" ที่ตกลงกันไว้ในบทสนทนาตอนวางแผน แล้วประกาศไว้ตรงๆ ว่า อย่าหยิบมาเป็น ticket ใหม่อีก:

  • ทุก artifact ต้องเป็น YAML/JSON อ่านได้ในโฟลเดอร์ลูกค้าเสมอ — สคริปต์จะไม่เขียนหน้ารีวิว HTML ลงในโฟลเดอร์ลูกค้าอีก
  • แอปตัวเดียวรันโดย operator สำนักงานบัญชีคนเดียว จัดการได้หลายบริษัทลูกค้า (โมเดล multi-client Dropbox แบบเดิม) — ไม่ใช่หนึ่ง deployment ต่อหนึ่งบริษัท
  • backend ต้องต่อยอดจาก sequencer prototype ตัวเดิม (ต่อยอด ไม่ใช่เขียนใหม่) — คำถามคือ "ทำยังไง" ไม่ใช่ "จะใช้ไหม"
  • ลำดับความสำคัญของหน้ารีวิว: ตัดออก/ข้ามก่อน แล้วค่อยหมวดหมู่บัญชี/กลุ่มเอกสาร
  • รูปแบบไฟล์ PEAK export คือเป้าหมายภายนอกที่ตายตัว — ไม่เปิดให้ออกแบบใหม่

กติกาชุดนี้เองที่ทำให้อีก 6 วันถัดมาเดินไปได้เร็ว — ทุกครั้งที่มีคำถามเชิงสถาปัตยกรรมโผล่มา คำตอบส่วนใหญ่ถูกตัดสินใจไว้แล้วในบทนี้
