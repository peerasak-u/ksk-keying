บทที่ 9 — ภาคผนวก

ถ้าจะติดตั้งใช้งานจริง ต้องมีอะไรบ้าง

คอนโซลนี้เบากว่าที่คิด — งานหนักทั้งหมดเกิดที่ API ของ Anthropic ไม่ใช่บนเครื่องที่รัน ของจริงที่ต้องมีคือสิทธิ์เข้าใช้ ไม่ใช่แรงเครื่อง (รวมทางที่ตรงที่สุดสำหรับเครื่อง Windows ไว้ท้ายบท)

console/ ไม่ใช่แอปที่ต้องการเครื่องแรง — มันเป็น Bun process เดียวที่คอย spawn claude CLI เป็น child process สั้นๆ ต่อ stage งานประมวลผลจริง (การอ่านเอกสาร ตีความ จัดหมวดหมู่) เกิดขึ้นที่ API ของ Anthropic ไม่ใช่บนเครื่องนี้ นี่คือเหตุผลว่าทำไม deployment จริง ของโปรเจกต์นี้เอง — เว็บบล็อกเล่มนี้ที่คุณกำลังอ่านอยู่ก็เช่นกัน — รันอยู่บน Raspberry Pi ได้สบายๆ

สิ่งที่ต้องมีจริง

สิ่งที่ต้องมีรายละเอียด
Bun ตัวเดียวที่ต้องมี ไม่ต้องมี Node.js เลย — console/server.ts รันตรงจาก TypeScript ผ่าน Bun.serve() ไม่มีขั้นตอน build ตอนรัน (ทดสอบจริงกับ Bun 1.3.14; Docker image ทางการอิง oven/bun:1)
claude CLI ที่ล็อกอินแล้ว console ไม่มีระบบ auth ของตัวเองเลย มันแค่ shell เข้า claude binary ที่ล็อกอินไว้บนเครื่องอยู่แล้ว (subscription plan หรือ API key ก็ได้) — ต้องล็อกอินเสร็จ ก่อนรัน console
โฟลเดอร์ .claude/ ของ skill/agent ต้อง "เดินขึ้นไปเจอ" ได้จาก cwd ที่ sequencer สั่งรัน — รันตรงบนเครื่องจะเจอเองถ้า workspace อยู่ใต้ repo เดียวกัน แต่ในคอนเทนเนอร์ Docker ต้อง mount เข้าไปเอง ไม่งั้น /ksk-keying จะเงียบๆ กลายเป็น no-op ที่รายงานว่า "เสร็จ" ทั้งที่ไม่ได้ทำอะไรเลย
อินเทอร์เน็ตขาออก HTTPS ไปยัง Anthropic API เท่านั้น (เมื่อ KSK_ENGINE=claude) — ไม่มีการเรียกออกอื่นใดจากตัวเซิร์ฟเวอร์เอง ไม่มี telemetry
พื้นที่ดิสก์ console/runs/ เก็บ event log (.jsonl) ต่อการรันแบบไม่มีวันลบเอง — เพิ่มไปเรื่อยๆ ตามจำนวนรันจริง ไม่มีการ rotate ในตัว ต้องวางแผนพื้นที่ระยะยาวเอง นอกเหนือจากพื้นที่ของโฟลเดอร์ลูกค้าเองซึ่งแปรผันตามขนาดเอกสารสแกน
เครือข่ายที่เข้าถึง localhost เท่านั้นโดย default (127.0.0.1) — ไม่มีชั้น auth ของตัวเอง จะเปิดให้เข้าจากเครื่องอื่นได้ก็ต่อเมื่อเป็นเครือข่ายส่วนตัวที่ยืนยันตัวตนแล้วเท่านั้น (README แนะนำ Tailscale IP ตรงๆ) — ห้าม bind 0.0.0.0 หรือเปิดสู่ LAN/สาธารณะเด็ดขาด

ฮาร์ดแวร์: เบากว่าที่คิด

เพราะการอนุมานของโมเดลเกิดที่ฝั่ง API ไม่ใช่บนเครื่อง ความต้องการ CPU/RAM ของตัว console เองจึงต่ำมาก — พอสำหรับรัน Bun process เดียวและ spawn child process สั้นๆ ต่อครั้งเท่านั้น ไม่ต้องมี GPU และเนื่องจากทั้งระบบมีคิวเดียวทั่วทั้ง console (บทที่ 4) งานจะไม่มีวันขนานกันจนต้อง การทรัพยากรมากกว่านั้น — เครื่องระดับ Raspberry Pi รันได้จริง (ดูอย่างที่เห็นตรงนี้)

สองเส้นทางติดตั้ง

ทางตรง: bun console/server.ts

ค่า default ทั้งหมดชี้เข้า mock mode — ไม่แตะ claude binary จริง ไม่มีค่าใช้จ่าย และสร้าง demo workspace ให้เองทันที เหมาะสำหรับลองระบบก่อน จะชี้ไปที่ workspace ลูกค้าจริงและ engine จริงต้องตั้งอย่างน้อย KSK_ENGINE=claude และ KSK_WORKSPACE_ROOT=/path/to/client/workspace

ทาง Docker: docker compose up

Image ตั้งต้นจาก oven/bun:1 ติดตั้ง claude CLI ด้วย native installer ตัวเดียวกับที่ใช้บน host (เพื่อให้ credential file ที่ mount เข้ามาอ่านได้ด้วย CLI build ที่เข้ากันได้) และสร้างผู้ใช้ที่ไม่ใช่ root ด้วย UID/GID ตรงกับ host เพื่อให้ไฟล์ credential ที่ bind-mount เข้ามา อ่าน/เขียนได้โดยไม่ต้องไล่ chmod เอง

ข้อจำกัดที่เอกสารระบุไว้ตรงๆ

docker-compose.yml ใช้ network_mode: host เพื่อให้ค่า default bind 127.0.0.1 ของ server.ts ยังเป็นจริงเหมือนรันตรงบนเครื่อง — วิธีนี้ใช้ได้เฉพาะ Linux เท่านั้น ถ้าจะรันบน Docker Desktop (macOS/Windows) ต้องสลับไปใช้ ports: ["127.0.0.1:4820:4820"] และแก้ server.ts ให้ bind 0.0.0.0 แทน — ยังไม่มีใครทำการปรับนี้จริงในโค้ดตอนนี้

สิ่งที่ต้อง mount เข้าคอนเทนเนอร์เพื่อให้ทำงานได้จริงกับ engine จริง: โฟลเดอร์ workspace ลูกค้า, โฟลเดอร์ .claude/ ของ skill/agent จาก repo host (อ่านอย่างเดียวพอ), โฟลเดอร์ runs/ (ไม่งั้นประวัติการรันหายทุกครั้งที่ rebuild container), และไฟล์ credential ของ claude CLI สองไฟล์จาก host (~/.claude/.credentials.json แบบอ่าน-เขียน เพราะ CLI รีเฟรช token แล้วเขียนกลับ, กับ ~/.claude.json ที่ไม่บังคับแต่แนะนำ เพื่อข้ามหน้าจอ onboarding ที่จะทำให้ headless spawn ค้าง)

สิ่งที่ไม่ต้องมีก็ได้

Tailwind CLI เป็นแค่ devDependency สำหรับคอมไพล์ style.src.css → style.css ตอนพัฒนาเท่านั้น — ไฟล์ style.css ที่คอมไพล์แล้วถูก commit ไว้พร้อมใช้ ไม่ต้องมี Tailwind หรือขั้นตอน build ใดๆ เพื่อแค่รันเซิร์ฟเวอร์ ต้องมีก็ต่อเมื่อ จะแก้ CSS เองเท่านั้น

ถ้าเครื่องเป้าหมายเป็น Windows

ไม่มีใครทดสอบ path นี้จริงในซีรีส์นี้ — โค้ดเองก็ยังต้องปรับก่อนถึงจะรันได้ (ดู "ข้อจำกัด" ด้านบน) แต่จากสิ่งที่เอกสารในโปรเจกต์ระบุไว้ตรงๆ บวกกับพฤติกรรมมาตรฐานของ Docker Desktop พอสรุปเป็น คำตอบตรงคำถามได้สามข้อ

Docker ใช่ ง่ายสุดจริง — และพิมพ์จาก PowerShell ได้เลย

ไม่ต้องเปิด WSL shell เองแยกต่างหาก พิมพ์ docker compose up จาก PowerShell ตรงๆ ได้ ข้อเท็จจริงที่อาจไม่ตรงกับที่คิดไว้คือ: Docker Desktop บน Windows ใช้ WSL2 เป็น engine เบื้องหลังอยู่แล้วโดย default มาตั้งแต่รุ่นเก่าๆ — ไม่ว่าจะสั่งงานจาก PowerShell, CMD, หรือ WSL shell เอง คำสั่ง docker ทุกตัวก็วิ่งผ่าน WSL2 VM เดียวกันอยู่ดี ต่างกันแค่ "หน้าต่างที่พิมพ์คำสั่ง" ไม่ใช่ "ตัวที่รันงานจริง" — ดังนั้นความกังวลเรื่อง "จะวุ่นวายกับ WSL" ไม่มีทางเลี่ยงได้แม้จะตั้งใจไม่ยุ่งกับมันเลยก็ตาม แต่ข่าวดีคือมันไม่ต้องยุ่งเองจริงๆ — Docker Desktop จัดการ WSL2 ให้ทั้งหมดอยู่แล้ว

Performance: เบาพอ แต่มีจุดคอขวดเดียวที่ควรรู้

CPU/RAM ของงานจริง (spawn claude CLI สั้นๆ ต่อ stage, serve API เบาๆ) ไม่ใช่ปัญหา — WSL2 เป็น VM ที่เบามาก virtualization overhead ต่ำกว่ายุค Hyper-V/Docker Toolbox เก่ามาก ส่วนที่ควรรู้ไว้มีจุดเดียว: I/O ข้ามขอบเขตไฟล์ระบบ Windows↔Linux — ถ้า bind-mount โฟลเดอร์ workspace ลูกค้าจาก C:\Users\... ตรงๆ เข้าคอนเทนเนอร์ การอ่าน/เขียนไฟล์จำนวนมาก (PDF หลายร้อยหน้า, JSON ย่อยต่อกลุ่มเอกสาร) จะช้ากว่าไฟล์ที่อยู่ในระบบ ไฟล์ของ WSL2 เองล้วนๆ อย่างเห็นได้ชัด เพราะต้องผ่านสะพานแปลระบบไฟล์อีกชั้น — งานของ console นี้ เบาพอที่จะไม่เจ็บตัวมากในการใช้งานทั่วไป แต่ถ้าลูกค้ามีเอกสารสแกนเยอะมากต่อเดือน การย้าย workspace มาเก็บในระบบไฟล์ของ WSL2 เอง (ผ่าน \\wsl$\...) จะเร็วกว่า bind-mount ข้ามจาก Windows ตรงๆ อย่างมีนัยสำคัญ

Volume สำหรับ auth: ใช้ .env ชี้ไปที่โปรไฟล์ Windows ตรงๆ ได้ ไม่ต้องตั้งอะไรใหม่

docker-compose.yml อ้าง credential ผ่านตัวแปร HOST_HOME (ดูช่วง "สิ่งที่ต้อง mount" ด้านบน) — บน Windows ค่าที่ต้องใส่ใน .env คือ path โปรไฟล์ผู้ใช้ ตรงๆ ด้วย forward slash เช่น HOST_HOME=C:/Users/ชื่อผู้ใช้ ที่เก็บ .claude/.credentials.json และ .claude.json ซึ่งเป็นไฟล์เดียวกับที่ Claude Code เวอร์ชัน native บน Windows สร้างไว้ให้อยู่แล้วตอนล็อกอินครั้งแรก Docker Desktop แชร์ทั้งไดรฟ์ให้อัตโนมัติเป็นค่าเริ่มต้นอยู่แล้ว (เปิดอยู่โดย default ในเวอร์ชันปัจจุบัน) จึงไม่ต้อง เปิด "File sharing" เพิ่มเอง แค่แก้ไฟล์ .env ไฟล์เดียวก็พอ — ใช้ไฟล์ .env แทนการ export ตัวแปรใน PowerShell เพราะ docker compose อ่านไฟล์นี้ เหมือนกันทุก OS ไม่ต้องมานั่งจำ syntax ตัวแปรของ PowerShell แยกต่างหาก

สิ่งที่ยังต้องแก้ในโค้ดก่อน ไม่ใช่แค่ตั้งค่า

ตามที่ระบุไว้ในหัวข้อก่อนหน้า — network_mode: host ใช้ไม่ได้แบบเดียวกับ Linux บน Docker Desktop ต้องสลับ compose ไปใช้ ports: ["127.0.0.1:4820:4820"] คู่กับแก้ server.ts ให้ bind 0.0.0.0 ภายในคอนเทนเนอร์ก่อน ถึงจะเข้าถึง จากฝั่ง Windows host ได้ — เป็นงานที่ต้องทำครั้งเดียวตอนพอร์ต ไม่ใช่ปัญหา performance แต่เป็นช่องว่างของโค้ดที่ยังไม่มีใครปิดจริงในตอนที่เขียนบทนี้
